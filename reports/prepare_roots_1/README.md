# PREPARE-ROOTS-1 — Prepare и Tradeable в `map_actions`

Ветка `codex/prepare-roots-1`. Режим экспериментальный и **выключен по умолчанию**: без флага поведение Policy, импортёра, LIVE и
всех shadow-режимов совпадает с `main` (проверено ниже). Модели, веса, датасеты, Collector и сырые логи не менялись.
В отчёте нет сырых логов и имён игроков; только id карт и счётчики.

## 1. Что оказалось в протоколе

Карта с `Prepare` или `Tradeable` в руке всегда даёт ровно **два root** на одну сущность (на 84 матчах — ни одного исключения):
оба `type=POWER`, одинаковый `mainEntity`, одинаковые параметры. Названия вариантов в сообщении нет.

Что реально различает варианты (по 62 выбранным игроком root-ам Prepare; метка проверялась по следующему публичному блоку и тегу
`IS_USING_PREPARE_OPTION=1` — они допустимы только как проверка, не как вход):

| Ситуация в `DebugPrintOptions` | Что выбрал игрок | Блок после `SendOption` | n |
|---|---|---|---|
| один root `NONE`, второй `REQ_ENOUGH_MANA`, при этом `COST > mana >= DECK_ACTION_COST` | legal root | `DECK_ACTION` (Prepare) | 42 из 42 |
| один root `NONE` без целей, второй `REQ_TARGET_TO_PLAY` | legal root | `DECK_ACTION` | 1 из 1 (ещё 14 невыбранных случаев согласуются) |
| оба `NONE`, ровно один перечисляет цели (таргетная карта) | root с целями → обычный розыгрыш; без целей → Prepare | `PLAY` / `DECK_ACTION` | 16 из 16 |
| оба `NONE`, цели не различают (миньон) | различает только порядок (`PLAY` перед `DECK_ACTION`, 3 из 3) | — | не принято |

* Невалидные root-ы идут в списке после валидных. Поэтому «первый валидный» ничего не говорит о роли при одном валидном варианте;
  роль определяют арифметика маны и код ошибки. **Порядок вариантов в реализации не используется нигде.**
* Prepare-действие стоит `DECK_ACTION_COST` (1) маны, `SendOption` для него — `selectedTarget=0`, `selectedPosition=0`.
* **Tradeable (`CORE_SW_072`)**: два root-а есть (13 решений с двумя доступными root-ами), но ни одного собственного выбора игрока нет. Чужие
  Trade в логах идут тем же блоком `DECK_ACTION` с тегом `IS_USING_TRADE_OPTION`, но роли root-ов для своих действий не доказаны.
  `TRADE_CARD` **не реализован**: такие решения остаются отклонёнными.

## 2. Что реализовано

* `map_actions(..., prepare_actions=False)` (`src/manamind/integrations/powerlog/policy_actions.py`): правила таблицы выше; два невалидных
  root-а не дают действий и больше не вызывают `AMBIGUOUS_SELECTION`; всё остальное (оба валидных миньона, Tradeable, один root у
  Prepare-карты, неизвестная ошибка, sub-options, цели у Prepare-root) отклоняется.
* Новый тип действия `PREPARE_CARD` использует **существующий** столбец `prepare_card` (схема действий 4): входы и checkpoint не меняются.
  Поля как у `PLAY_CARD` (id карты, эффективная цена, `hand_index`), `play_position=0`, без цели. Меню сохраняет все допустимые действия:
  обычный розыгрыш и Prepare — два разных действия с разными хешами.
* `domain/policy_action.py`: `ACTION_TYPES` (версия 1) не тронут; добавлены `PREPARE_ACTION_TYPES` и `PREPARE_ACTION_SCHEMA_VERSION = 2`.
  Строка датасета, в меню которой есть `PREPARE_CARD`, получает `action_schema_version: 2`; загрузчики версии 1 её **отклоняют**
  (`validate_example`), то есть молча в обучение она попасть не может.
* Импортёр (`extract_match(..., prepare_actions=True)`): подтверждение метки блоком `DECK_ACTION` для Prepare и `PLAY` для обычного розыгрыша;
  несовпадение → решение отбрасывается как `UNSUPPORTED_DECISION_KIND`.
* `policy_v2.encode_policy_v2` теперь связывает `PREPARE_CARD` с тем же токеном руки, что и `PLAY_CARD` (раньше такой тип попал бы в ветку
  «стол»). Policy v1 и v3 принимают тип без изменений (v3 использует кодировщик v2).
* LIVE: `PolicyRecommender(..., prepare_actions=True)`, `run_manamind.py --prepare-actions`, `replay_live_recommendations.py --prepare-actions`,
  `model_shadow_eval.py --prepare-actions`; тексты для оверлея и панели («ПОДГОТОВИТЬ (Prepare)»).

## 5. Модели и риск

Все четыре checkpoint (ML-1C v1, frozen Policy v2, Retrained v2, Policy v3) загружаются без миграции и считают меню с `PREPARE_CARD`
(431 решение, средний размер меню 14,3; логиты конечны; веса не менялись — проверено тестом на неизменность `state_dict`).

**Но ни один checkpoint не обучался на `prepare_card`.** Норма входного столбца `prepare_card` (0,27–0,29) равна норме столбцов
`trade_card` и `choose_card`, которые тоже ни разу не использовались, а у frozen и retrained v2 эти значения совпадают
(общая инициализация, градиента не было). Это начальные веса, а не выученное. Техническое измерение, не качество: если закодировать Prepare
как `PLAY_CARD`, первый выбор меняется в 1 (frozen v2), 14 (retrained v2), 11 (v3) и 12 (v1) решениях из 431. Совпадение первого выбора
модели с реальным `PREPARE_CARD` игрока на 48 решениях (23 / 32 / 39 / 22 из 48 у v3 / frozen v2 / retrained v2 / v1) **нельзя считать оценкой**:
остальные решения тех же матчей входили в обучение, независимой контрольной выборки нет. Поэтому режим по умолчанию выключен, а в LIVE
он подписан как эксперимент.

Другие shadow-режимы при меню с `PREPARE_CARD`: Outcome Shadow возвращает `UNSUPPORTED` по каждому Prepare-действию (63 из 63), Strategy Shadow
оценивает меню целиком, Model Shadow и его оценка различают `PLAY_CARD` и `PREPARE_CARD` по типу и хешу действия. Без флага ни один из них
не получает такого действия.

## 7. Оставшиеся ограничения

1. Миньоны Prepare с двумя доступными root-ами (`JAIL_721`, `JAIL_912`, `JAIL_321`) различимы только порядком; порядок не принят как основание.
   Варианты: принять порядок явным решением владельца с контролем по следующему блоку или оставить отказ.
2. `TRADE_CARD` не реализован: нет ни одного собственного выбора игрока для Tradeable.
3. `prepare_card` не обучен ни в одной модели; рекомендации с этим действием не проверены. Для обучения нужны размеченные примеры (схема строк
   версии 2 уже отделена от версии 1) и отдельное решение об обучении. Не делалось и не запускалось.
4. Правило `REQ_TARGET_TO_PLAY` подтверждено одним выбором игрока.
5. Побочная находка вне задачи: сущность с переводом строки внутри `entityName` ломает `hslog` (`RegexParsingError`), отдельный матч от 12 октября.
