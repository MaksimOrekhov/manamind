## 0. Коротко

**Ответы на три вопроса**

1. **Насколько полно ManaMind теперь знает карты из реальных партий?** По наличию записи — полностью: **52 669 из 52 669**
   появлений (100 %, 906 из 906 уникальных ID) в эффект-зонах 150 разрешённых матчей находят ровно одну запись в новом
   снимке. Было 72,5 %. Ориентир ≥ 98 % выполнен. По глубине картина другая: запись с полными ключевыми полями — 97,2 %
   появлений, текст целиком разбирается существующей грамматикой — **24,9 %**, эффект объявлен в ManaEngine — 11,8 %
   (без изменений). «Есть запись» и «эффект понятен» — разные утверждения (раздел 4).
2. **Сколько новых карт и токенов нашлось?** Снимок вырос с 36 022 до **36 390** записей: **+369 новых ID** и 1 исчез.
   Из них 288 относятся к набору `BE`: набор вырос с 13 записей (4 коллекционные) до **300 (135 коллекционных)**. Для игры
   значимы 226 новых записей (132 коллекционные, 94 токена и прочие создаваемые). Но главный источник «новых для
   ManaMind» карт — не патч, а **область старого источника**: 27 851 из 28 220 ID, отсутствовавших в старом
   коллекционном файле, уже существовали в клиентских данных старой сборки как неколлекционные (токены, Locations,
   оружие, зачарования, другие режимы). В реальных партиях из 27,5 % потерянных появлений **17,2 п. п.** вызвала область
   старого источника и **10,3 п. п.** — выход BE.
3. **Можно ли переходить к проверке перевода текстов в Card IR?** Да, массового отсутствия исходных данных больше нет: у
   каждой карты из реальных партий есть запись и текст. Но есть три ограничения, которые нужно решить в самом пилоте
   (раздел 8): в новом снимке 323 коллекционные карты имеют **артефакт текста** (`&` после `</b>`, запятой или точки) и 10 —
   отладочный хвост; для 18 ID из набора `TIME_TRAVEL`/`CATACLYSM` нет `cardClass`; у **50,5 %** появлений есть признак,
   по которому одного текста недостаточно (пул случайного выбора, скрытая информация, счётчик истории, состояние).

**Неожиданные находки [ФАКТ]**

- **Старый закреплённый каталог — не сборка 253932.** Профиль датирован 2026-10-01 (патч 36.6.3), но его коллекционный
  файл идентичен коллекционной части сборки **253216** (патч 36.6.0), записи байт в байт; от сборки 253932 он отличается
  четырьмя картами. Эта же сборка 253216 — клиент, на котором сыграны старые матчи (раздел 1.2).
- Три сборки клиента (254477, 255026, 255130) опубликованы с **побайтно одинаковым** `cards.json`. Данные 37.0.0 не
  менялись между ними, поэтому сборка 255130 точно описывает матчи на сборке 254477.
- Патч 36.6.3 (сборка 253932) **не добавил ни одного ID**; все 369 новых записей пришли с 37.0.0.
- Из 578 записей, различающихся между снимками, только **9 коллекционных карт вне BE** изменили поля правил. Остальное —
  артефакты текста (276), метаданные без правил (87), неколлекционные записи, в основном Battlegrounds (180), разметка
  (19) и 7 записей BE. Балансных правок в данных — порядка пяти карт (раздел 3.3).

**Главные риски, найденные по ходу работы**

1. Текст в новом снимке нельзя отдавать парсеру «как есть»: артефакты `&` и `~GAMEPLAY ASPROXY …`. Слой чистит их
   (`plain_text`, `strip_text_artifacts`), сырая запись не меняется.
2. Тест `test_the_shadow_file_rotates_instead_of_growing_without_bound_or_losing_rows` нестабилен на чистом `main`
   (раздел 7.3) и не связан с этой работой.

### 1.2 Как привязаны к клиенту [ФАКТ]

Номер сборки клиента пишется в `Power.log` (`BuildNumber=…`). Читались только эти числа и только у разрешённых матчей:

| Группа | Матчей | Сборка клиента |
|---|---:|---|

| OLDER (82) | 64 | **253216** у всех 64 |

Следствие: OLDER описывается снимком 253216, NEWER — снимком 255130 (= 254477). Для 18 старых матчей сборка не
подтверждена; по датам они ранние, но это предположение.

### 1.3 Чего установить нельзя

- Номер сборки **текущего** клиента пользователя на момент чтения отчёта неизвестен: последние матчи имеют 254477, а клиент
  мог обновиться. Данные 37.0.0 в HearthstoneJSON одинаковы для всех трёх сборок, но гарантии для следующего патча нет.
- Снимок — сторонний разбор клиентских файлов [ВНЕШНЕЕ]. Мы не сверяли его с самим клиентом. Появление артефактов
  текста (раздел 3.4) показывает, что разбор может меняться между сборками.

### 1.4 Хранение

`data/card_metadata/`: два файла `hearthstonejson_<сборка>_enUS.json.gz` по 1,6 МБ и `manifest.json`. Сжатие gzip с
фиксированным заголовком; идентичность задаёт SHA-256 **распакованных** байт из манифеста (SHA сжатого файла не
закреплён: он зависит от версии zlib). Новая сборка рядом со старой, ничего не перезаписано. Полный снимок
промежуточной сборки 253932 в репозиторий не добавлен; её разница с 253216 перечислена в разделе 3.3 и воспроизводится
загрузкой.

## 2. Структура и назначение слоя

| Элемент | Назначение |
|---|---|
| `src/manamind/card_metadata/snapshot.py` | `CardMetadata.load()` читает снимок офлайн, проверяет SHA-256 и размер; `lookup/get/describe/records/ids_for_dbf_id`; `quality_flags`; `plain_text`, `strip_text_artifacts` |
| `.../compare.py` | детерминированное сравнение двух снимков с разбиением различий по причинам |
| `.../coverage.py` | статусы текста и уровни покрытия для ID из реальных состояний (без привязки к данным) |
| `.../text_features.py` | эвристики семейств механик и «особых случаев» |
| `scripts/fetch_card_metadata_snapshot.py` | закрепить сборку (`--build`), никогда не перезаписывает; `--verify` сверяет с источником |
| `reports/card_metadata_2/` | воспроизводимые инструменты этого отчёта и их результаты |
| `data/card_metadata/README.md` | контракт слоя |

Поведение, которое потребовалось от слоя:

- Тип, стоимость, класс, ключевые слова, текст и снимок-источник доступны через `describe()`.
- Токены и неколлекционные карты находятся тем же вызовом (`is_token`, `collectible`).
- Отсутствующий ID — `Status.MISSING`, `get()` возвращает `None`. Дубликат — `Status.AMBIGUOUS`; `get()`/`describe()` бросают
  `AmbiguousCardId`. В реальных снимках дубликатов нет (36 390 уникальных ID и `dbfId`).
- Неполные и подозрительные записи помечаются независимыми флагами и **не** исправляются.
- **Изоляция:** ни один модуль вне пакета не импортирует его; `CardCatalog` и словари его не читают; профиль Standard на него не
  ссылается. Всё это проверяют тесты (раздел 7).

Слой не задаёт легальность в формате. Карта есть в снимке, но в Standard-профиль она не попадает автоматически: 135
коллекционных карт BE присутствуют в слое, а в каталоге модели из них нет более 100.

Корпус: **150 матчей, 5 142 решения, 52 669 появлений, 906 уникальных ID** в эффект-зонах — те же числа, что в baseline.
Сила героя считается отдельно (как в baseline); `opponent_known_cards` по-прежнему пусто. Воспроизведение:
`measure_coverage.py --data-root <data>`, результат — `coverage.json`.

Источники: **A** — старый (каталог модели ∪ коллекционный снимок, как в baseline); **B** — полная старая сборка 253216

## 6. Ограничения корректности, полноты и актуальности

**Корректность.**
- Снимок — сторонний разбор клиентских файлов; с клиентом не сверялся. Артефакты текста в сборках 254477+ показывают, что
  выход разбора может меняться без изменения игры.
- Флаги качества и «особые случаи» — эвристики: отсутствие флага не доказывает простоту карты.
- «Запись найдена» не проверяет, что текст на экране игрока в тот момент совпадал со снимком. Для старых матчей
  использовать снимок 253216 (раздел 4.5).
- Карты с `MULTI_STATE_TEXT` (`@`) и `{0}` хранят в одной строке несколько состояний или значения, вычисляемые во время
  игры: «(2 left!)@(Ready)@…», «Summon a {0}/{1}». Из строки их значения не восстановить.

**Полнота.**
- Только `enUS`. Нет данных о пулах генерации (Discover, случайный выбор), `entourage`, запретах пулов и скрытых
  тегах правил (например `DONT_PICK_FROM_SUBSETS`): в HearthstoneJSON этих полей нет; они есть в `hsdata/CardDefs.xml`.
- У 105 записей нет `cardClass`; у 1 643 игровых записей нет текста (в основном ванильные миньоны, оружие и служебные
  карты режимов).
- Слой не содержит правил формата, ротации и запретов. Пока достаточно того, что «запись есть» и «можно положить в
  колоду Standard» разведены. Для Deck Builder правила нужны отдельно.

**Актуальность.**
- Снимок отражает патч 37.0.0.255130 от 2026-10-15; следующий патч снова сделает часть данных устаревшей. Нужна процедура:
  `fetch_card_metadata_snapshot.py --build N`, затем `compare_snapshots.py` старый → новый. Автоматического обновления нет
  намеренно.
- Сборка текущего клиента пользователя не проверялась (раздел 1.3).
- 18 старых матчей не имеют установленной сборки.

### 8.5 Условия, без которых пилот даст искажённый результат

1. Подавать парсеру `strip_text_artifacts(text)`, а не сырой текст (раздел 3.4).
2. Решить заранее, как IR выражает `{0}`/`@` (значение во время игры; несколько состояний), и считать такие карты отдельной
   категорией выразимости.
3. Пул Discover/random нужен из другого источника (`hsdata/CardDefs.xml` или официальное описание): в HearthstoneJSON его нет.
   Не угадывать пулы по тексту.
4. Для 18 ID без `cardClass` класс не подставлять; помечать как неизвестный.
5. Выборку брать только из разрешённого корпуса (`fresh_holdout` исключать по ID до чтения), независимо от обучавших
   данных; для OLDER-матчей использовать текст снимка 253216.
6. Решение по Turn Engine (EXECUTOR-BAKEOFF-0) пилотом не принимается: пилот измеряет выразимость и точность перевода текстов,
   а не исполнение.

## 9. Воспроизведение

Из корня рабочей копии (игнорируемые `data/` лежат только в основной; `--data-root` указывает на них):

```powershell
python -I scripts\fetch_card_metadata_snapshot.py --build 255130 --verify
python -I reports\card_metadata_2\compare_snapshots.py --output <новый json>
python -I reports\card_metadata_2\measure_coverage.py --data-root E:\ManaMind\data --output <новый json>
python -I reports\card_metadata_2\card_ir_readiness.py --data-root E:\ManaMind\data --output <json> --candidates <json>
python -I reports\card_metadata_2\verify_compatibility.py --main-checkout E:\ManaMind --output <json>
```

Все скрипты читают данные, выводят агрегаты без ID матчей, имён игроков и строк логов и не перезаписывают существующие
файлы. Сравнение снимков (`compare_snapshots.json`) воспроизводится в тестах байт в байт без локальных данных; покрытие,
готовность Card IR и совместимость требуют локальных игровых данных и checkpoint и в CI не запускаются.

Файлы отчёта: `compare_snapshots.json`, `coverage.json`, `card_ir_readiness.json`, `card_ir_pilot_candidates.json`,
`compatibility.json`.
