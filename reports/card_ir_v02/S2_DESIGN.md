# S2 — изменяемые параметры экземпляра карты (проектное решение)

**Решение:** в v0.2 S2 **не реализован**. Torch (`CATA_585`) остаётся честным PARTIAL с явной CORE-зависимостью
`instance_parameter` и квитанцией пропуска ([examples/CATA_585.json](examples/CATA_585.json),
[examples/gap_bindings.json](examples/gap_bindings.json)). S2 — следующая отдельная задача; ниже — проект, который она
должна реализовать или опровергнуть. Статическая подстановка урона (`$8` при каждом розыгрыше) запрещена: после
первого возврата она даёт неверное число.

## 1. Что требуется Torch

Подтверждено пользователем (игровой опыт, не документация Blizzard; в декларациях — `basis: USER_OBSERVED`):

| Наблюдение | Следствие для языка |
|---|---|
| Исходный урон 8 | начальное значение параметра берётся из текста (`$8`) |
| 8 в существо с 3 Health → Torch возвращается с уроном 5 | после удара параметр становится равен избытку |
| 5 в существо с 2 Health → возвращается с уроном 3 | новое значение читается при следующем розыгрыше |
| Нулевой избыток → не возвращается | возврат условен: `excess > 0` |
| Divine Shield → избыток 0, не возвращается | избыток считается от **фактически нанесённого** урона, а не от `8 − Health` |
| Значение сохраняется между розыгрышами | параметр принадлежит экземпляру и переживает cast → hand |

Неизвестно: Spell Damage (тег `ImmuneToSpellpower`), Immune-цель, полная рука, копирование Torch, перемешивание
в колоду.

Важная поправка к аудиту Opus: в CARD_AUDIT 3.11 Divine Shield был сведён к той же формуле `max(0, 8 − h)`.
Наблюдение пользователя (избыток 0) это опровергает. Поэтому Torch нужен **не только** S2, но и значение
«фактически нанесённый урон этого удара» (`damage_result`): `excess = max(0, dealt − health_before)`.

## 2. Почему v0.2 этого не выражает

* Число урона — литерал декларации; у `ENCHANT` нет числового слота, кроме атаки, здоровья и Spell Damage.
* `R_RETURN_TO_HAND` (новое правило v0.2) **сбрасывает** состояние существа при возврате; Torch требует обратного
  для своего параметра. Смешивать эти механизмы через зачарования нельзя.
* Значение `var` живёт только в одной резолюции; между розыгрышами его нет.

## 3. Варианты

| Вариант | Суть | Плюсы | Минусы |
|---|---|---|---|
| **A. Объявленные параметры экземпляра** (рекомендуется) | `params` в декларации, чтение `{"param", "of"}`, операция `SET_PARAM` | явный, проверяемый, не зависит от зачарований; одна и та же модель для Torch, «Improves» и счётчиков `{0}` | новый вид состояния у сущности; нужны политики зон/копий |
| B. Числовой слот зачарования | `ENCHANT {set_param}` | переиспользует `R_ENCHANTMENT` | противоречит сбросу при возврате и Silence; смысл зависит от того, что такое зачарование у заклинания в руке |
| C. Свободные теги клиента | писать в IR номера тегов игры | ближе всего к клиенту | утечка деталей реализации; теги не документированы; нарушает «данные, а не код» |

Гипотеза для проверки (HYPOTHESIS, не факт): клиент хранит такие числа в тегах сущности (например, семейство
`TAG_SCRIPT_DATA_NUM_*`) и показывает их в тексте через плейсхолдеры. Если Power.log это подтвердит, вариант A
получит наблюдаемый аналог для live-наблюдения, но в IR всё равно должны остаться **именованные** параметры, а не
номера тегов.

## 4. Проект варианта A

### 4.1 Какие данные принадлежат экземпляру

```json
"params": {
  "damage": {"initial": {"n": 8, "mark": "$"}, "persist": "ENTITY", "copy": {"unknown": "copy_policy"}}
}
```

* Параметр принадлежит **сущности** (экземпляру карты), не ID карты и не игроку. Две копии Torch в руке
  независимы.
* `initial` — литерал из текста (сверка чисел и меток `$`/`#` как сейчас).
* Видимость: значение экземпляра в руке SELF видно игроку (текст карты), значит, может быть входом модели; значение
  экземпляра соперника видно, только если карта раскрыта. Никогда не подставлять значение по умолчанию вместо
  неизвестного (контракт AGENTS.md: маски пропусков).
* Метаданные карты (`$8`) остаются базовым значением; текущее значение — отдельное поле экземпляра (тот же принцип,
  что «base metadata отдельно от current cost/stats»).

### 4.2 Как изменяется

* `{"op": "SET_PARAM", "to": SELF|{"ref"}, "param": "damage", "value": <value>}` — только объявленный параметр, только
  сущность этой карты или явно связанная; значение вычисляется в момент шага (как `set`).
* Чтение: `{"param": "damage", "of": "SELF"}`; в `DEAL_DAMAGE.amount` метка `$` переходит от `initial` к чтению.
* Для Torch дополнительно нужно `{"dealt": "<bind of the damage op>"}` — фактически нанесённый уроном шага (это
  отдельный элемент, близкий к `R_DAMAGE_EVENT_AMOUNT`; Divine Shield → 0).

### 4.3 Как сохраняется между зонами

`persist` — одна из политик, всегда явная:

| Политика | Смысл | Пример |
|---|---|---|
| `ENTITY` | живёт, пока жива сущность, через любые зоны | Torch (cast → hand), «Improves each use» |
| `ZONE` | сбрасывается при выходе из текущей зоны | счётчики прогресса «while holding this» (кандидат) |

Перемешивание в колоду и возврат существа (`R_RETURN_TO_HAND`) — граничные случаи: для `ENTITY` по умолчанию
**не определено**, требуется зависимость, пока Power.log не покажет, сохраняется ли ID сущности.

### 4.4 Copy и Transform

* **Transform** создаёт новую сущность новой карты: параметры берутся из её `initial` (согласовано с
  `R_TRANSFORM`).
* **Copy** (`copy_of`): копируются ли текущие параметры — UNKNOWN (`R_COPY` в v0.1 тоже UNKNOWN). В S2 поле `copy`
  обязательно: `"CURRENT"`, `"INITIAL"` или `{"unknown": dep}`; неуказанная политика — ошибка валидатора.

### 4.5 Инварианты валидатора (для задачи S2)

1. Каждый `param`/`SET_PARAM` ссылается на объявленный параметр; каждый объявленный параметр читается.
2. `initial` проходит сверку чисел текста; метка `$` не теряется и не появляется.
3. `SET_PARAM` только для `SELF` или `ref`; не на произвольный селектор.
4. `persist` и `copy` явны; `{"unknown": dep}` требует UNKNOWN_RULE-зависимости.
5. Lint: «with any excess», «improves», «(N left!)» ↔ наличие параметра; параметр ↔ такая формулировка.

### 4.6 Conformance-сценарии (будущий исполнитель)

| Сценарий | Ожидание |
|---|---|
| Torch 8 → существо 3 Health | возврат с 5 |
| Torch 5 → существо 2 Health | возврат с 3 |
| Torch 3 → существо 3 Health | нет возврата |
| Torch → существо с Divine Shield | урон 0, нет возврата |
| Torch(5) в руке, розыгрыш позже | бьёт на 5 |
| Две копии Torch | независимые значения |
| Spell Damage +1, полная рука, Immune, копия Torch | **UNKNOWN** — зависимости, а не ожидание |

## 5. Можно ли использовать для других карт

Экран стандартного каталога (1 189 коллекционных карт `standard_scope_20261001.json`, регулярные выражения по
тексту — счёт упоминаний, не семантика):

| Признак | Карт | Примеры |
|---|---:|---|
| клиентские плейсхолдеры `{0}`/`{1}` | 32 | Felwood Treant `({0} left!)`, Ultraxion |
| improve/upgrade | 18 | Omen «Improves after this attacks!», Amirdrassil «Improves each use!» |
| excess (нужен `dealt`, не обязательно S2) | 8 | Sindragosa's Triumph, Briarspawn Drake |
| return this to hand | 2 | Torch, Eternal Firebolt (последний не меняет числа — S2 не нужен) |

То есть механизм не карточный: «улучшающиеся» карты и счётчики прогресса — та же модель «число на экземпляре,
меняется эффектом, читается текстом». Критерий из IR_V02_PROPOSAL (≥ 3 карт выборки) выполнится на следующей выборке,
если в неё попадут карты «Improves».

## 6. Сложность для исполнителя

* **Хранилище** — простое: словарь параметров на сущности, сериализуемый вместе с состоянием.
* **Сложные места** — правила, а не код: сохранение при перемещениях, копии, Silence (для существ), видимость для
  наблюдения. Каждое из них сейчас UNKNOWN и должно стать зависимостью, а не догадкой.
* **Наблюдение (live/Policy)** — отдельная работа: нужно доказать, что текущее значение извлекается из Power.log
  для SELF-карт, и добавить его в схему признаков с маской. Это вне Card IR и требует отдельного разрешения.

Оценка: реализация A в языке — того же порядка, что весь v0.2 (словарь, валидатор, рендер, lint, 30–40
conformance-случаев); исполнитель — небольшая структура данных плюс 4–6 правил, большинство из которых сначала нужно
подтвердить логами.

## 7. Почему не сейчас

* В 12 картах B1 S2 нужен одной карте; второй нужный элемент (`dealt`) тоже нужен только ей.
* Без подтверждения политик зон и копий S2 добавил бы видимость полноты при скрытых предположениях — ровно то, от
  чего защищает строгий режим.
* Пользователь предпочёл отдельную задачу. Torch при этом не проигнорирован: его пропуск связан квитанцией,
  CORE-зависимостью и этим документом.

Рекомендуемая следующая задача: **CARD-IR-S2** — реализовать вариант A + `dealt` с conformance-сценариями раздела
4.6, затем проверить Power.log-ом (ID сущности после возврата, теги числа) до того, как объявлять Torch FULL_DEP.
