# LIVE-MVP — Diagnose Late Recommendations

**Вывод: Power.log в этих реальных партиях позволяет получать рекомендации ДО выбора действия.**
Главный подтверждённый дефект находится в lifecycle legal menu / SettleGate. Меню появляется
заранее, но потребляется в промежуточной точке окончания одного task list. Следующий UI task list
инвалидирует snapshot, после чего использованное меню уже нельзя предложить снова. Между последним
task list и действием игрока бывают десятки секунд без READY. Это воспроизводится без collector,
inference и Tkinter. Минимальное исправление реализовано; статус — **REPLAY VERIFIED, новый реальный
playtest ещё требуется**.

## Хронология реальных решений

Время `Power.log` — timestamp строки клиента. `Δ read` — время её первого наблюдения из
`tail_trace.jsonl`. Несколько строк одного batch имеют одинаковое `Δ read`: порядок строк известен,
но отдельное время обработки каждой строки не измерено. Read clock монотонный и не является UTC;
журнал отдельно записывает UTC перед вызовом панели. Время реального repaint Tkinter не записывается.

нового меню после служебных задач. Удержание рейтинга по номеру хода эту ошибку не решает.

## Проверенные гипотезы и исправление

- **SettleGate / потребление меню — подтверждено.** `_try_emit()` вызывался после каждой строки.
  При End n gate временно settled, `take_ready()` удаляет pending и запоминает options ID как
  emitted. Следующий DebugDump n+1 снимает READY. Закончившиеся позднее списки уже не имеют pending.
- **`q_ended >= q_created` не отключён.** В рассмотренных примерах списки полностью заканчиваются
  заранее; дефект возникает между очередными маркерами и после потребления pending. Данных для
  ослабления этой проверки нет.
- **`supersede()` остаётся необходимым при новом GameState.** SendOption/изменение состояния удаляют
  как pending, так и сохранённое меню. UI-only task-list markers не подменяют authoritative GameState.
- **Options доступны заранее.** Например, options 5 получены через 125 ms после начала хода и за
  25.407 s до SendOption. Новый источник данных или реконструкция кандидатов из неполного состояния
  для устранения этого дефекта не требуются.
- **Collector / inference / Tkinter не объясняют потерянные десятки секунд.** Дефект полностью
  воспроизводится в чистом session replay. Frozen v2 replay: median inference 3.094 ms,
  p90 4.329 ms, p99 5.669 ms (локальный запуск; это не измерение live cold start).
  Начало/конец collector scan, inference и repaint в этих recordings не записаны: их точную live
  задержку вычислить нельзя. Синхронная работа может добавлять задержку, но не является необходимой
  причиной воспроизведённого дефекта. Большой промежуток между trace rows сам по себе не доказывает
  блокировку: silent polls обычно в trace не сохраняются.

Изменения ограничены `live/session.py` и `live/gate.py`:

1. Проверка готовности выполняется после полного read batch / tick, а не между его строками.
2. Уже проверенное меню сохраняется только для повторной проверки после новых client task lists.
   Новый список сразу скрывает рейтинг. После завершения всех списков меню проходит обычные
   SELF/privacy/state проверки и получает новый seq и рейтинг.
3. Любой superseding GameState, новое options message, SendOption, reset или отказ доверия
   очищает сохранённое меню. Таймер отображения не добавлен; settle timeout остаётся fail closed.

Policy, её checkpoint, GameState/encoder, collector и UI не изменены.

## Измерения replay до и после

Здесь **snapshot/READY не означает рекомендацию**: mapper ещё может отказать, а реальная панель
ещё должна получить и отрисовать результат. Повторные snapshots одного options ID после задач
не считаются отдельными пользовательскими решениями.

| Метрика | Ранняя запись: до → после | Последняя запись: до → после |
|---|---:|---:|
| Snapshots | 39 → 57 | 54 → 81 |
| Snapshots, актуальные в конце batch | 15 → 57 | 22 → 81 |
| Инвалидации от DebugDump | 35 → 21 | 52 → 30 |
| Уникальные меню с READY до действия | 39 → 38 | 54 → 53 |
| Меню, READY которых доживает до SendOption | 4 → 36 | 2 → 51 |
| Уникальные меню, оценённые v2 в исправленном replay | 32 | 51 |
| Из них финальная оценка доживает до SendOption | 30 | 49 |
| Отказы mapper, считая повторные snapshots | 8 AMBIGUOUS_SELECTION | 4 AMBIGUOUS_SELECTION |
| Исторический журнал: показано рекомендаций | 10 | 11 |
| Исторический журнал: median времени до инвалидации | 926.850 ms | 844.711 ms |
| Исторический журнал: min…max времени | 117.818…2983.233 ms | 57.010…1173.416 ms |

Итого исправленный replay: **91 уникальное актуальное меню**, **83 оценённых меню**,
**79 оценённых меню сохраняют последнюю оценку до SendOption**. Получено 138 snapshots,
126 расчётов и 12 отказов mapper. Во второй исторической записи дополнительно 9 DISCARDED
во время inference и 2 UNAVAILABLE / AMBIGUOUS_SELECTION. Это отдельные наблюдаемые причины,
не предположение о знаниях или уверенности нейросети.

Пять меню исправленный код не выпускает: игрок отвечает до окончания ожидаемых задач / до
устойчивой границы batch. Часть старых transient snapshots поэтому намеренно исчезла. Повышать
количество snapshots ценой актуальности нельзя. Task-list инвалидации тоже остаются: в ожидании
незаконченных задач старый рейтинг не показывается.

## Что ещё проверить в клиенте

При следующем пользовательском playtest: после начала собственного хода и после медленного PLAY
дождаться конца анимаций **до следующего клика**; рейтинг должен появиться/обновиться и оставаться
пока решение актуально. Во время новых задач он скрывается, после их завершения пересчитывается.
После SendOption, смены доверия или окончания игры старый рейтинг не должен возвращаться.
Для очень быстрых действий окно объективно может быть коротким; AMBIGUOUS_SELECTION остаётся
ограничением существующего mapper. Это исправление не объявляет LIVE-MVP пригодным к игре до
повторной реальной проверки пользователем. Новые источники данных, обучение и архитектура не внедрялись.
