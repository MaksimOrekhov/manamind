# CARD-IR-EXECUTION-PILOT-1 — исполнение Card IR через существующий ManaEngine

**Вывод: CONDITIONAL GO.** Вертикальный путь `Card IR → шаги ManaEngine → изменение состояния → проверка`
работает на существующем движке **без единого изменения нативного кода** и без карточных обработчиков: 4 карты,
4 универсальных нативных шага (`DAMAGE`, `HEAL`, `BUFF_FRIENDLY_MINIONS`, `DISCARD_RANDOM_SPELL`) плюс Overload и
Lifesteal, 21/21 сценариев и 25/25 мутаций совпали с ожиданиями, записанными вручную заранее. Мутации доказывают, что
расчёт определяет IR: 11 исполнимых мутаций дали 11 результатов, отличных от прежней декларации движка (0 совпадений
с контролем «только card_id»), 14 остальных отвергнуты с типизированной причиной. Условие — у движка нет пути
загрузить реальную позицию, а реальные партии показывают взаимодействия, которых нет ни в IR-декларации, ни в движке
(раздел «Находки»).

Протокол (гипотеза, baseline, критерии) зафиксирован отдельным коммитом `60cc942` до написания кода:
[protocol.json](protocol.json). Архитектура — [ARCHITECTURE.md](ARCHITECTURE.md), каждый сценарий —
[SCENARIOS.md](SCENARIOS.md), машинные результаты — [RESULTS.json](RESULTS.json).

## Исследование выполнимости (до кода)

| Вопрос | Ответ |
|---|---|
| 1. Какие операции IR уже есть в ManaEngine? | `DEAL_DAMAGE`, `RESTORE_HEALTH`, `ENCHANT` (только +N/+N всем своим существам), `pay discard` случайного заклинания школы, `seq`, Overload, Lifesteal. Ещё есть шаги без пилотной трансляции: `DRAW`, `GAIN_ARMOR`, `FREEZE`, `SUMMON_FIXED`, `DESTROY_MINION`, `MODIFY_HERO_ATTACK`, `MODIFY_WEAPON_ATTACK`, `GRANT_HEALING_BONUS`, Choose One |
| 2. Можно ли транслировать декларацию в представление движка? | Да, для подмножества: у движка уже есть декларативный список шагов `EFFECT_COMPOSITION` (14 видов × 19 селекторов) со строгим разбором и нативной проверкой каталога. Для двух карт трансляция побайтно равна существующей декларации движка; две другие (Bolt, Drain) переходят с именованных обработчиков на универсальные шаги |
| 3. Что реализовано и проверено? | Конвейеры урона (Spell Damage `CURRENT_AT_STEP`) и лечения (бонус, ограничение по максимуму), фаза смертей, Overload, сброс, легальность целей по селекторам, failure funnel. Нативные тесты CTest и 337 адаптерных тестов зелёные; правила урона/лечения в словаре IR — PROJECT_REVIEWED |
| 4. Можно ли получить состояние и применить действие через API? | Да, но только прототипная сессия из колод: `GameSession` + обычные ходы + `attempt_action` на клоне. Подходит для детерминированных сценариев |
| 5. Что мешает произвольному состоянию? | Нет импорта наблюдаемого `GameState` (ENGINE-STATE-IMPORT-0: 0/1227 реальных позиций гидрируемы); любая карта без декларации в руке отравляет позицию; классы только Mage/Priest/Hunter/Warrior; нет правил игрока (например, «лечение наносит урон») |
| 6. Порядок эффектов и привязка целей? | Для `seq` — прямо: порядок шагов сохраняется, движок сам держит границы шагов и смерти. Цель одна на действие; IR-привязка `bind`/`ref` отображается в явный селектор, а ссылка на ранее выбранное множество — только при доказанной эквивалентности |

Новый движок, импортёр состояния или переработка C++ для минимального исполнения **не понадобились**, поэтому
реализация продолжена.

## Выбор карт

Пересечение всех деклараций Card IR (pilot_1, примеры v0.2, финал независимой проверки) с каталогом ManaEngine дало
28 карт; только 4 имеют статус FULL, нет зависимостей и отображаются на существующие универсальные шаги:

| Карта | Конструкции IR | Прежняя реализация в движке |
|---|---|---|
| Lightning Bolt `CORE_EX1_238` | `DEAL_DAMAGE $3`, CHOSEN CHARACTER ANY, `OVERLOAD 1` | именованный `TARGET_DAMAGE` |
| Flash Heal `CORE_AT_055` | `RESTORE_HEALTH #5`, CHOSEN CHARACTER ANY | `EFFECT_COMPOSITION` |
| Drain Soul `CORE_ICC_055` | `LIFESTEAL`, `DEAL_DAMAGE $3`, CHOSEN MINION ANY | именованный `LIFESTEAL_DAMAGE` |
| Overheat `FIR_906` | `seq`: ENCHANT ALL FRIENDLY +1/+1 (`as`), `pay discard RANDOM NATURE` → ENCHANT `ref` +1/+1 | `EFFECT_COMPOSITION` |

CATA_452 (FULL_DEP: токен + аура стоимости), Torch, Ultraxion, Aviana и карты с триггерами/аурами/пулами не
использовались. Декларации — копии файлов `card_ir_pilot_1` с одним изменённым полем `ir: card-ir/0.2`
([declarations_manifest.json](declarations_manifest.json) хранит SHA-256 исходников); все четыре строго приняты v0.2
как FULL без ошибок и предупреждений.

## Результаты

| Критерий протокола | Результат |
|---|---|
| C1 ≥ 2 универсальных операции IR → состояние | 4 вида нативных шагов + Overload + Lifesteal |
| C2 нет карточного кода | статическая проверка AST: 0 находок; транслятор не читает `card_id` (переименование карты не меняет шаги) |
| C3 поддержанные сценарии совпадают с независимыми ожиданиями | 21/21 (каждое поле видимого состояния; родитель не изменён; evidence debt нет) |
| C4 неподдерживаемое блокируется | 16/16 отказов и неисполнимых попыток с ожидаемым кодом; ничего не пропущено молча |
| C5 IR управляет расчётом | 25/25; 11 исполнимых мутаций ≠ прежняя декларация (B1 = 0); 14 отказов |
| C6 история не изменена | 0 изменённых отслеживаемых файлов; 8/8 исторических измерений Card IR воспроизведены побайтно (`verify_history.py`, включая `engine_mapping.py`); каталог регенерируется без diff |
| B0 совместимость со старыми декларациями | 18/18 сценариев дают идентичный результат (это совместимость, не истина) |

Мутации, которые **исполнились по IR** (не по карте): урон 3→5 (герой 25, а не 27); Overload 1→2; лечение 5→2;
`DEAL_DAMAGE`→`RESTORE_HEALTH` (та же карта лечит на 3 и всё равно даёт Overload); выбранная цель → «все вражеские
персонажи» (урон по герою и Sen'jin без выбора цели); сторона ANY→ENEMY/FRIENDLY и тип MINION→CHARACTER меняют
список легальных целей; удаление оплаченного шага Overheat оставляет +1/+1 и карту в руке; +2/+2 и +9/+9 исполняются
как написано. **Отвергнуты:** неизвестная операция и `DESTROY`, лишнее поле, метка `#` у урона, неиспользуемая цель,
перестановка шагов (ссылка до привязки), бафф врагов, +2/+1, шаг между привязкой и повторным выбором, бафф после урона,
PARTIAL, версия 0.1, а удаление Lifesteal или Overload отвергает нативная проверка каталога ManaEngine (механика карты
больше не представлена).

### Уровни доказанности (независимы)

| Карта | L1 валидация | L2 независимая семантика | L3 исполняется | L4 реальные партии (без holdout) | L5 обучение |
|---|---|---|---|---|---|
| Lightning Bolt | FULL | нет записи | 7/7 | урон = 3 в 4/4 наблюдениях без модификаторов | нет |
| Flash Heal | FULL | нет записи | 5/5 | 7/14 без модификаторов точно = min(5, недостающее); 5 — больше базы (невидимый бонус); **35/57 всех розыгрышей — лечение заменено уроном** | нет |
| Drain Soul | FULL | нет записи | 4/4 | 11/15 без модификаторов: урон 3 и лечение = нанесённому; overkill лечит полностью (2 + 5 наблюдений) | нет |
| Overheat | FULL | нет записи | 5/5 | наблюдений нет | нет |

L2 «нет записи»: эти четыре декларации в независимых проверках участвовали только в регрессионном воспроизведении.
L4 — согласие величины эффекта с наблюдениями EVIDENCE-0B, не воспроизведение именно этих позиций; «без
модификаторов» исключает наблюдения с конфаундерами `FOREIGN_*`, но эффекты игрока (бонус лечения, удвоение) в
наблюдении не видны. L5 всегда false: `training_eligible` сессий не меняется, и пилот ничего не допускает к обучению.

## Находки

1. **Реальные партии требуют правил, которых нет в декларации и в движке.** Flash Heal в 35 из 57 реальных
   розыгрышей нанёс урон (до 18) вместо лечения — действует правило игрока «лечение наносит урон»
   (`rule:HEALING_DOES_DAMAGE` в словаре IR есть, `R_AMOUNT_ORDER` — UNKNOWN). Декларация карты при этом верна:
   правило принадлежит другой карте/эффекту. Для тактического расчёта по реальной позиции нужен не только IR карты, но
   и представление действующих правил игрока — сейчас ни импорта, ни такого правила в ManaEngine нет.
2. **Дыра строгого валидатора v0.2 (не исправлялась — вне задачи).** Overheat с изменённым одним числом (`attack: 2`,
   `7`, `health: 9` или `n: 2` у сброса) принимается как FULL без предупреждений. Причина
   (`card_ir/validate.py::_check_numbers`): числа текста ищутся среди чисел IR, но немаркированные числа IR без пары
   в тексте не проверяются, а неявное `n: 1` («a random») даёт лишнюю «единицу». Изменение двух чисел ловится.
   В пилоте вред не дошёл до исполнения только потому, что движок не умеет неравные статы и `n ≠ 1`; при расширении
   трансляции такая декларация исполнилась бы. Прогнозы вердикта валидатора в 4 мутациях не совпали: стороны и типы
   цели валидатор ловит лучше, чем я ожидал (3), а +2/+1 пропускает (1).
3. **Неподдерживаемое движок блокирует корректно и типизированно:** бонус лечения на чужого персонажа →
   `HEALING_BONUS_SCOPE_UNREVIEWED`; карта без декларации в руке → позиция отвергнута целиком
   (`UNSUPPORTED_CARD_ENTERED_HAND`, сначала я ожидал `..._IN_ACTIVE_HAND`; ожидание кода исправлено, суть — нет).
4. **Семантические допущения трансляции явны:** бафф как базовые статы (`ENCHANTMENT_AS_BASE_STATS`, в движке нет
   Silence, поэтому ненаблюдаемо) и повторный выбор «них» (`REF_RESELECT_EQUIVALENT`, доказано только для промежуточного
   сброса). Правило оплаты при пустой доске (OH-4: заклинание сбрасывается) — `R_PAYMENT` UNVERIFIED, свидетельств нет.
5. **Граница пакетов.** Первая версия моста лежала в `src/manamind/integrations/manaengine/` и нарушила правило
   изоляции `card_ir`/`card_metadata` (два архитектурных теста упали). Мост перенесён в каталог отчёта; граница не
   ослаблялась.
6. Ошибки самого раннера, исправленные до финального прогона: сравнение «только эти поля» сначала смотрело на diff, а
   не на итоговые значения (LB-7); статическая проверка сначала ловила обобщённое `card_id in installed`.

## Ответы на вопросы задачи

1. **Нужен ли новый исполнитель?** Нет. Существующий `EFFECT_COMPOSITION` ManaEngine уже работает как backend для
   Card IR: строгий разбор, нативная проверка каталога и fail-closed сохраняются, а трансляция — тонкий слой.
   Ограничение не в архитектуре, а в узком словаре шагов движка и в отсутствии импорта позиции.
2. **Что из языка применимо уже сейчас:** `DEAL_DAMAGE`/`RESTORE_HEALTH` с метками `$`/`#`, CHOSEN-цели
   (CHARACTER ANY/ENEMY, MINION ANY, CHARACTER FRIENDLY), области ALL (4 для урона, 1 для лечения), ENCHANT +N/+N всем
   своим существам, `seq`, `pay discard` случайного заклинания школы, `ref` на привязанное множество при доказанной
   эквивалентности, ключевые слова OVERLOAD и LIFESTEAL у заклинаний.
3. **Масштабирование на десятки карт.** Для простых заклинаний — дёшево: у движка 46 деклараций `DATA_COMPOSITION`,
   но IR есть только для двух из них. Нужны (а) IR-декларации этих заклинаний и (б) ещё ~6 отображений в трансляторе
   (`DRAW`, `GAIN_ARMOR`, `FREEZE`, `SUMMON` с токеном — это FULL_DEP, `DESTROY`, атака героя). Миньоны (Battlecry),
   триггеры, ауры, условия и пулы требуют расширения нативного словаря шагов — это расширение замороженного движка и
   отдельная задача. Оценка автора: десятки простых заклинаний — реально; десятки произвольных карт текущего Standard —
   нет без роста ManaEngine.
4. **Правила, которым нужны игровые свидетельства:** замена лечения уроном и порядок с бонусами (`R_AMOUNT_ORDER`),
   бонус лечения на чужого персонажа и на Lifesteal, оплата сброса при пустой доске (`R_PAYMENT`), enchantment против
   базовых статов при Silence (`R_ENCHANTMENT`), правила легальности целей (`R_PLAY_TARGET` UNVERIFIED). Overload в
   реальных наблюдениях этой выборки не сверялся (факта долга Overload в наблюдениях нет).
5. **Что мешает тактике одного хода:** (а) нет импорта реальной позиции в ManaEngine — главный блокер; (б) любая
   неподдержанная карта в руке или на доске отвергает позицию целиком, а в реальных руках таких большинство;
   (в) действующие правила игрока (как «лечение = урон») не представлены; (г) полная информация клона запрещена для
   реального поиска без information-set дизайна.
6. **Минимальный следующий шаг с наибольшей пользой.** Отдельной задачей — проверить Card IR на *реальных* позициях
   без импорта в движок: для розыгрышей простых заклинаний из Power.log (без holdout) предсказывать непосредственные
   видимые последствия по IR-трансляции и сравнивать с наблюдением, с явным списком модификаторов, которые надо видеть
   (Spell Damage, бонус лечения, правила игрока). Это даёт измеримую пользу на настоящих данных и сразу показывает,
   каких правил игрока не хватает. Параллельно — маленькая правка валидатора (двусторонняя сверка чисел), тоже
   отдельной задачей, так как она меняет вердикты исторических проверок.
