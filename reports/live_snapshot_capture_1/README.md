# LIVE-SNAPSHOT-CAPTURE-1

## Цель и границы

Задача — понять, почему импортированные решения не всегда имеют соответствующий LIVE Snapshot, устранить подтверждённые потери в записи и дать Collector компактный послематчевый отчёт. Это не оценка Policy и не новый holdout.

Не открывались `fresh_holdout` и новые реальные Power.log. Исторические отчёты NEW-MATCHES-EVAL-2 и LIVE-JOIN-COVERAGE-1 не изменялись. Повторная оценка тех же 204 решений не проводилась: текущая задача касается сохранения будущих LIVE-наблюдений, а прежний набор уже использовался в исследовании.

## Аудит жизненного цикла

Поток остаётся прежним: `Power.log → LogTail → LiveSession trust/settle gate → LiveRunner → Recorder`, параллельно завершённую игру читает Collector и запускает существующие импортеры. Рекомендации и опциональные журналы shadow потребляют уже созданный доверенный Snapshot.

Установленные причины отсутствия снимков:

| Причина | Класс | Поведение |
|---|---|---|
| ManaMind не работал в момент решений | Ожидаемое ограничение | Collector всё ещё может сохранить завершённую игру. LIVE catchup молча восстанавливает ход партии и выдаёт только актуальное settled-решение; исторические меню задним числом не объявляются наблюдавшимися. |
| Меню ещё не settled, было заменено новым GameState/SendOption, отсутствовал SELF-контроль или нарушена целостность сущностей | Ожидаемый отказ trust gate | Snapshot не выпускается; причины остаются в статусах и счётчиках. Gate не ослаблялся. |
| Быстрая последовательность действий | Обычно ожидаемое ограничение | LogTail передаёт строки пакетами, а gate оценивает состояние после пакета. Уже заменённое меню не сохраняется как актуальное. |
| Collector и LIVE runner работают независимо | Ожидаемое различие каналов | Collector может импортировать игру без LIVE-снимков, например если процесс был закрыт. Теперь это явно отмечается в отчёте Collector. |
| Recorder выдавал `OSError` при записи | Подтверждённый дефект | Исключение проходило из `LiveRunner.step()` в общий LIVE-обработчик `UnifiedRuntime`; тот инвалидировал текущий результат и навсегда отключал рекомендации. Ошибка записи больше не ломает LIVE и Policy-путь; выводится безопасный стабильный код, попытки записи продолжаются. |
| Перезапуск приложения в той же партии | Подтверждённый дефект | Новый Recorder начинал счётчики строк с нуля и мог повторно дописать уже сохранённый префикс; новая `LiveSession` начинала `seq` с 1. Теперь существующая запись проверяется по `game_key` и точному префиксу `slice.log`, курсоры продолжаются с сохранённой длины, а sequence подхватывается из записанных Snapshots. Совпавшее текущее решение получает прежний seq; новый state получает seq выше сохранённого максимума. |
| Несовпадение истории при возобновлении | Неопределённость, безопасный отказ записи | Если старый `slice.log`, его trace или `game_key` не совпадают с текущим catchup, запись отклоняется fail-closed. LIVE runner и рекомендации продолжают работать; старая запись не переписывается. |

Отсутствующие исторические LIVE-снимки восстановить нельзя. Отчёт различает доверенные снимки, trust-отказы, ошибки записи и строгие несовпадения; если нет ни записи, ни наблюдения текущего процесса, он использует общий код `LIVE_NOT_OBSERVED_OR_NOT_RECORDED`. Только по отсутствию файла нельзя доказать, был ли выключен процесс или не смог записать Recorder.

## Изменения

- `LiveSession` считает распознанные пакеты Options, выпущенные доверенные снимки и отказанные причины. Это только диагностические счётчики; state, legal menu и решение Policy не меняются.
- `Recorder` безопасно продолжает совпавшую запись после рестарта, не дублирует один и тот же Snapshot при catchup-повторе, добавляет компактный `capture_summary.json` и проверяет возможность replay по уже записанному line count.
- `LiveRunner` изолирует сбои Recorder от LIVE-сессии, собирает безопасные коды ошибок и позволяет Collector получить краткую сводку наблюдений текущего процесса.
- После обработки завершённой игры Collector записывает `data/raw/collected/capture_reports/<game_key16>.json`. Отчёт содержит число решений по policy-импортеру, LIVE-счётчики, валидные Snapshot, строгие совпадения с импортированными размеченными решениями и найденные записи Prediction/Outcome Shadow/Strategy Shadow/Model Shadow. В нём нет копий полных состояний или сырых строк.
- Strict join не менялся. Строгое сравнение отчёта возможно для размеченных policy-решений с `state_hash`; пропущенные/неразмеченные решения учитываются отдельными счётчиками импортера, но не получают выдуманный identity.
- Для отчёта по конкретной партии ищите JSON по первым 16 символам `match_id` в `data/raw/collected/capture_reports/`. Обычная команда запуска не меняется; shadow-журналы появятся только если соответствующие опции уже включены.

## Регрессионные проверки

Проверки добавлены для:

- перезапуска на том же текущем решении: неизменный seq, один сохранённый Snapshot, исходный replay;
- перезапуска после продвижения партии: дописывается только не сохранённый суффикс, новое решение получает следующий seq, replay выдаёт те же state hash;
- ошибки записи диска: Snapshot всё ещё возвращается сессией в `READY`;
- UnifiedRuntime с ошибкой Recorder: рекомендация всё равно отображается, `live_failed` остаётся `False`;
- отчёта Collector при игре без LIVE-наблюдения;
- строгого сопоставления Snapshot, policy-примера и строки журнала.

Проверки:

- Целевые replay/runner/Collector/runtime тесты: **157 passed, 1 skipped**.
- Полный pytest на чистом архивном снимке закоммиченного проекта: **1173 passed, 2 skipped**.
- Полный Ruff на том же чистом снимке: **passed**.
- Ruff для изменённых файлов в рабочем checkout: **passed**.

Полный прогон в исходном рабочем каталоге сначала завершался единственным ожидаемым отказом теста
`test_no_submodules_or_vendored_engine`: он видит посторонний неотслеживаемый `vendor/RosettaStone`.
Ruff в этом каталоге также пытался прочитать сломанную вложенную `.ruff.toml` внутри `vendor`; чистый
снимок исключил эти посторонние артефакты и оба полных прогона прошли.

При полном pytest на Windows в существующих тестах Model Shadow печатались предупреждения
`Windows fatal exception: code 0xc0000008` / `access violation` из фонового потока
`policy_shadow/worker.py:_lower_thread_priority`. Сам pytest завершился успешно, **1173 теста прошли,
ошибок и падений нет**. Этот участок не менялся в задаче; это окруженческое предупреждение следует
отдельно исследовать в задаче Model Shadow, если оно воспроизводится в обычном запуске.

## Проверка после новых матчей

1. Запустить `scripts/run_manamind.py` обычной командой из `docs/LIVE_BRIDGE.md`; менять аргументы не требуется.
2. После завершения матча открыть свежий JSON из `data/raw/collected/capture_reports/`.
3. Проверить `collector.power_log_decisions`, `live.status`, `live.snapshots_saved`, `live.valid_trusted_snapshots` и `strict_identity.labeled_policy_decisions_with_exact_snapshot`.
4. Если `live.status` — `NO_LIVE_RECORDING`, процесс не сохранил запись или не наблюдал игру. Если `LIVE_OBSERVED_NO_RECORDING` и есть `recording_failures`, запись не создалась. `RECORDING_PARTIAL` означает, что доверенных снимков выпущено больше, чем найдено на диске; `recording_failures` показывает ошибки записи. Если есть `trust_rejections`, это отказ trust gate. Если strict count ниже числа размеченных policy-решений, просмотреть `labeled_policy_decisions_without_exact_snapshot`; сопоставление не ослаблять.
5. Проверить `journals.rows_by_kind` для реально включённых журналов. Нулевой счётчик сам по себе не доказывает ошибку: optional shadow мог быть отключён.

Подтверждение реальной надёжности записи требует нескольких новых матчей с работающим процессом. Этот код не может восстановить решения, принятые до запуска, и не доказывает покрытие для исторических 666 решений.
