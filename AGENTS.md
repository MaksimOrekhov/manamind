## Product goal

Build a desktop Hearthstone assistant that observes a live game and recommends strong legal lines of play. It must advise the player; it must not automate mouse movement, clicks, or gameplay.

The long-term architecture is:

```text
Hearthstone / game logs → adapters → player-visible GameState
→ legal action generation and simulator → policy/value models and search
→ recommendations → Vue 3 / Tauri UI or overlay
```

The first milestone is deliberately narrower: a small, understandable **Value Network v1** that estimates `P(SELF eventually wins | visible GameState)`. It evaluates positions; it does not select moves. Do not build a simulator, Policy Network, MCTS, self-play, OCR, overlay, or card-text language model as part of this milestone unless the user asks to start that next phase.

## Non-negotiable modeling principles

- Keep game rules in a simulator, not in the neural network. The RosettaStone bridge is the current simulator integration prototype; do not treat its synthetic-checkpoint predictions as demonstrated game strength.
- Do not assign context-free strength scores to cards. Estimate a position from the board, resources, cards, and other visible context.
- Orient every observation to `SELF` and `OPPONENT`; the value target is always for SELF: `1.0` win, `0.0` loss, `0.5` draw.
- Never expose hidden opponent hand identities, deck order, future draws, or hidden RNG outcomes to model input. Use hand size and explicitly revealed cards only.
- Support unknown/new card IDs without failing inference. Combine identity embeddings with structured card properties; report unknown IDs to the caller.
- Keep base card characteristics separate from current board-entity state. Preserve board positions and support variable-size zones.
- Prefer correctness, clarity, tests, and extensibility over premature performance or generic frameworks. Explain material architectural changes briefly.
- The user is a frontend developer learning Python/ML. Explain new Python/ML concepts in plain language when they matter; answer in Russian by default.

## Current implementation (2026-09)

- Python 3.12+, PyTorch, NumPy, and PyYAML; CUDA is available on the primary Windows machine, but code must also run on CPU. Device selection is CUDA → MPS → CPU.
- Domain types, card catalog and vocabulary live under `src/manamind/domain` and `src/manamind/cards`. `GameState` requires `turn_number` and `active_player` (`SELF`/`OPPONENT`), with player-visible SELF/OPPONENT observations.
- Encoding under `src/manamind/encoding` produces a 27-value global vector plus encoded card zones. Card/entity vectors combine ID/category embeddings, normalized numeric features, presence masks, mechanics, and entity flags. Visible SELF hand order and hero-power readiness are encoded. Numeric scaling is signed `log1p` with clipping at 10,000.
- `src/manamind/models/value_network.py` implements a compact shared entity encoder, masked mean/max pooling for variable-size zones, a global-feature MLP, fusion MLP, and a win/loss logit (sigmoid for probability).
- `src/manamind/training` contains synthetic data generation, JSONL serialization/loading, group-by-`game_id` train/validation/test splitting, training, metrics, baselines, and checkpoints. Synthetic data is only a pipeline sanity check; it is not real Hearthstone supervision and must never be presented as playing strength.
- Checkpoints include model config/weights, vocabulary, catalog snapshot, feature names, normalization settings, and encoder schema version. The current encoder schema is v4; older checkpoints must be rejected rather than silently interpreted with changed feature semantics.
- Inference is in `src/manamind/inference`; `predict_state.py` loads a checkpoint's catalog by default and can report unknown card IDs. `benchmark_inference.py` measures single-state and batch latency.
- RosettaStone is checked out at `vendor/RosettaStone` (revision `e10749b`), built as `pyRosetta` plus the ManaMind native bridge under `integrations/rosettastone`. The Python adapter offers `inspect_decks(...)`, `validate_deck(s)` against pinned engine metadata, `make_simple_test_deck(...)`, persistent `SimulatorSession(...)` with supported basic actions (including Location activation) and terminal result reporting, and `integrations/rosettastone/rollout.py` for weak baseline matches. Keep legal-action enumeration consistent with the engine’s final validators (including attack targets and full minion boards); baseline rollouts also guard against actions that make no visible progress. Sample lists are in `data/samples/rosettastone_test_decks.json`. Rollouts save both player-visible perspectives with labels in the existing JSONL schema (`source=rosettastone_baseline`). The current Standard metadata catalog is refreshed by scripts/update_card_catalog.py from HearthstoneJSON and filtered by data/cards/standard_sets.json; update that manifest at each rotation. Real labeled dataset runs use data/cards/standard_current_enUS.json by default when it exists, unless --cards is specified. RosettaStone now recognizes the current Standard set IDs through its card-set enums; current card metadata is loaded from a separate overlay. There is still no current ban list or complete current-card effect coverage. User-authorized simulator training is currently restricted to the audited Mother Drake Warlock list in `data/samples/mother_drake_warlock_selfplay.json`; do not treat those pilot results as Value Network labels or evidence of general Standard strength. The `BE_036` M.O.T.H.E.R. hand-card choice is supported as a `CHOOSE_CARD` action; Spire of Solitude (`JAIL_511`) exposes `ACTIVATE_LOCATION` and summons a size-matched Shivarra Infiltrator that attacks a random enemy minion; most other Discover/card-choice and mechanics/actions remain unsupported. Baseline labels are not a claim of model strength. Status, license, build, usage, and information-safety notes are in `docs/ROSETTASTONE_INTEGRATION.md`.
- The user explicitly started the next phase: a first policy-gradient self-play prototype lives in `src/manamind/integrations/rosettastone/policy.py` and `train_selfplay.py`. It scores currently legal actions from visible global features, public board summaries, ordered SELF hand card embeddings, and semantic action descriptors including card identity and hand position. RosettaStone entity IDs are never policy inputs; they are used only to apply legal actions. Both seats share one stochastic policy; terminal rewards are +1/-1/0 and one REINFORCE update follows each game batch. The policy checkpoint is separate from the Value Network. Use `evaluate_policy.py` to test greedily on held-out seeds against the fixed heuristic baseline, with both policy seats, both deck orders, baseline-vs-baseline control, and optional `--opponent-checkpoint` comparisons. This remains a learning-loop prototype, not established game strength; many effects and the full current Standard pool remain future work. Default output is `checkpoints/policy_selfplay_v1.pt`; use `--resume` to continue. Legacy action-policy checkpoints migrate compatible feature weights and start a fresh optimizer state. See run instructions and limitations in README.md and docs/ROSETTASTONE_INTEGRATION.md.
- Preliminary policy run: `checkpoints/policy_selfplay_v1.pt` was trained on 16 self-play games, seeds 101–116. On 10 held-out seeds with both seats and both deck orders (40 games), it scored 33/40 against the very weak fixed baseline (Wilson 95% interval 68.0%–91.3%). Baseline-vs-baseline control was 12–8. In a direct factorial comparison against its deterministic untrained initialization, the trained policy scored 20–20 (40 games; interval 35.2%–64.8%): no improvement is demonstrated yet. Reports: `reports/policy_vs_baseline_factorial_seed40001_10pairs.json` and `reports/policy_vs_initial_seed101_factorial_seed30001_10pairs.json`. Treat these as simulator-policy pilot results only, not Hearthstone strength.
- The up-to-date card catalog is ready, but this is not sufficient real-game training data. Existing synthetic and RosettaStone baseline examples are not evidence of current-game strength. Optional `replays` dependencies provide `hslog`; `scripts/audit_power_log.py` checks one local Power.log for Ranked + Standard + a complete result. `scripts/import_power_log.py` converts an eligible one-game log to local-only JSONL at pre-PLAY/ATTACK decision points from the local player's perspective, using the final match result as label. It strips names, does not reveal opponent hidden hand identities, and skips exact duplicate imports by comparing state sequences. Keep raw logs and resulting data in Git-ignored `data/raw/` and `data/processed_real/`. Multi-game logs are rejected until mode metadata can be associated reliably per game. Split entire matches as groups; never train/evaluate meaningfully on one match. See `docs/REAL_MATCH_DATA.md` for capture/import instructions.
- Important entry points: `generate_synthetic.py`, `train_value.py`, `train_selfplay.py`, `evaluate_policy.py`, `predict_state.py`, and `benchmark_inference.py`. Config is in `configs/value_v1.yaml`; sample inputs are in `data/samples`.
