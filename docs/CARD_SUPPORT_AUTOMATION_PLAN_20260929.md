# Масштабируемое добавление карт: анализ и план

Дата исходного плана: 2026-09-29. Текущий порядок работ с 2026-09-30 задан в [STANDARD_REGISTRY_PLAN_20260930.md](STANDARD_REGISTRY_PLAN_20260930.md): полный Standard registry, graph, классификация и вычисляемые gates до новой волны карточных реализаций. Пять колод остаются контрольными; прежние очереди и раздел «следующее действие» ниже сохранены как исторический контекст и не определяют текущий приоритет. Два generator-пилота реализованы; общий registry/admission gate пока планируется. Историческое сообщение ниже о блокировке bridge дубликатом `Choice::~Choice()` не воспроизвелось при последующей сборке; актуальное ограничение и smoke описаны в [WORK_SESSION_PROGRESS_20260930.md](WORK_SESSION_PROGRESS_20260930.md).

Исходное дополнение к ТЗ сохранено в [CARD_SUPPORT_AUTOMATION_ADDENDUM_20260929.md](CARD_SUPPORT_AUTOMATION_ADDENDUM_20260929.md). Этот план уточняет предложенную архитектуру на основании кода. Он заменяет прежний порядок работы «выбрать следующую карту и отдельно пройти весь цикл».

## 1. Вывод и рекомендуемое решение

Направление дополнения верное: единицей разработки должна стать проверенная возможность движка и пакет использующих её карт. RosettaStone уже умеет составлять эффекты из задач. Предлагается небольшой декларативный формат, описывающий эти существующие конструкции, и детерминированная генерация обычных C++ CardDef. Сложные эффекты остаются в native C++ и подключаются по именованному, проверенному обработчику.

Не начинать с нового интерпретатора игровых правил. Сначала доказать полезность генератора на небольшой выборке. Если аудит покажет, что шаблонов и общих C++ helpers достаточно, остановиться на них. Если после прототипа сборка окажется главным остаточным расходом, отдельно рассмотреть загрузку деклараций при старте в те же объекты Tasks/CardDef, сохранив текущий исполнитель.

Полностью заменить стоимость O(число карт) на O(число механик) нельзя: у каждой карты остаются параметры, требования к целям, источники правил и проверка. Сократить можно повторяющееся написание C++, подготовку сценариев, поиск аналогов и число сборок. Процент автоматизации и ускорение пока неизвестны; 60–80% из дополнения — гипотеза, не установленный результат.

Текущая задача завершает анализ и фиксирует план. Реализация инфраструктуры, новые карты, обучение и оценка модели — последующие этапы.

## 2. Что подтверждено исходниками

| Наблюдение | Основание | Следствие |

Два Warlock-списка проходили реальные запуски симулятора и обучение. Это эмпирически проверенные пилотные колоды; полного доказательства поддержки всех возможных генераций и взаимодействий пока нет. Прежнее краткое название «полностью поддержаны» нужно понимать с этим ограничением.

### Повторяющиеся реализации

- `CORE_CS2_004`: AddEnchantmentTask + DrawTask + требования к выбранному миньону. Хороший кандидат для декларации и проверки зачарования как зависимости.
- `END_007`: DamageTask + временное зачарование героя + DrawTask + ArmorTask. Подходит для проверки последовательности операций и окончания временного эффекта.
- `CORE_SW_066`: SilenceTask + требования к цели; отдельно нужны семантика необязательной цели Battlecry и действие Tradeable. Короткий C++ блок не означает, что всю карту уже можно автоматически допустить.
- `CAP_801`: зачарование + Reborn. Кандидат для композиции; характеристики, Taunt, Silence и Reborn проверяются отдельно от факта успешного розыгрыша.
- `CATA_302`: сейчас полное лечение написано через CustomTask, хотя есть HealFullTask. Это кандидат на устранение дублирования после проверки различий TakeHeal/TakeFullHeal, триггеров и модификаторов лечения.
- `CATA_582`: есть обычные задачи и ручное изменение счётчика Fire-spell. Счётчики истории следует проверить на единственный источник обновления, чтобы не переносить возможное двойное начисление в шаблон.
- `CAP_105`: DiscoverTask и SummonTask уже компонуются; для генератора важны продолжение после выбора и порядок появления существ.
- `CAP_806`, `EDR_846`, `FIR_959`: история событий, созданные карты, изменяемые экземпляры и широкие случайные пулы. Они нужны как сложные контрольные примеры; не являются хорошим первым набором для автоматического переноса.

Это качественная выборка из проверенного кода. Распределение всех 74 карт по классам автоматизации ещё не вычислено.

## 3. Какие существующие конструкции использовать

| Возможность | Существующие конструкции | Что обязательно уточнить в capability registry |
|---|---|---|
| Урон / лечение | DamageTask, HealTask, HealFullTask | Источник эффекта, Spell Damage, Lifesteal, иммунитет, момент обработки смертей |
| Добор / броня / мана | DrawTask, ArmorTask, ManaCrystalTask, TempManaTask | Переполнение руки, fatigue, постоянный/временный ресурс |
| Призыв / уничтожение | SummonTask, SummonCopyTask, DestroyTask, DestroyAllTask | Вместимость поля с Locations, порядок смертей, ownership |
| Создать / переместить карту | AddCardTask, PutCardDeckTask, ReturnHandTask, MoveToDeckTask | Новый экземпляр или перенос существующего; позиция и владелец |
| Усиление / Silence / Freeze | AddEnchantmentTask, Enchant, Effect, SilenceTask, FreezeTask | Длительность, снимаемость, копирование, активная зона |
| Цели / условия / последовательности | EntityType, playReqs, IncludeTask, FilterStackTask, ConditionTask, FlagTask | Типы объектов, обязательная/необязательная цель, snapshot списка, стек результатов |
| Discover / случайность | DiscoverTask, DiscoverCriteria, RandomCardTask, RandomMinionTask | Точный legal pool, повторения, продолжение выбора, доступность через bridge |
| Триггеры / ауры / стоимость | Trigger, Aura, SelfCondition, RelaCondition, AdaptiveCostEffect | Владелец события, зона активности, порядок, Silence, очистка и копирование |
| Квесты / составные карты | QuestProgressTask, CardProperty | Наличие поля в структуре ещё не означает реализацию конкретной новой механики |

Registry должен хранить не только названия, но и разрешённые сочетания параметров, ограничения, путь реализации и проверяющие сценарии. Наличие класса в C++ — лишь кандидат capability, пока его контракт не проверен.

## 4. Сравнение вариантов

| Вариант | Плюсы | Стоимость/риск | Решение |
|---|---|---|---|
| Общие C++ helpers и шаблоны | Минимальное вмешательство, быстрый старт | Ручное описание карт остаётся | Использовать сразу там, где полноценный формат не окупается |
| Узкий формат → C++ CardDef | Сохраняет игровой runtime; код можно читать и проверять; совместим с doctest | Нужны validator, генератор, подключение к CMake | Основной кандидат для прототипа |
| Формат → создание Tasks при старте | Карточные данные можно менять без перекомпиляции C++ | Дополнительный loader, lifecycle, диагностика и контроль версии | Рассматривать после измерения прототипа |
| Отдельный универсальный интерпретатор эффектов | Большая свобода описания | Дублирование порядка событий, смертей, выбора и аур | Не включать в первый этап |

Выбор codegen предварительный. Он подтверждается только после измерения труда, ошибок и времени сборки на пилоте. Не переписывать работающие карты массово ради самого формата.

## 5. План выполнения и критерии завершения

### Этап 0. Зафиксировать воспроизводимую базу

1. Сохранить версии/хеши исходного каталога, Standard-манифеста, пяти decklists и изменённого дерева правил. Один Git revision недостаточен при локальных изменениях vendor.
2. Повторно получить инвентарные 74/64/10, явно сохранив старый смысл этого отчёта.
3. Зафиксировать известные рабочие сценарии, команды сборки и места артефактов. Не запускать обучение для проверки инфраструктуры.
4. Начать учитывать затраты по стадиям: поиск правил, описание, генерация, компиляция, сценарии, исправления. Хронометраж прошлых сессий не позволяет объявить сборку главным bottleneck.

Результат: baseline manifest и краткий отчёт измерений. Готовность: другой запуск может воспроизвести тот же состав и понять происхождение бинарника.

### Этап 1. Аудит возможностей и количественная классификация

1. Скриптом собрать кандидаты из Tasks, Triggers, Auras, Conditions, CardProperty, targeting и существующих сценариев. Сканер не должен считать заголовок доказательством поддержки.
2. Вручную проверить контракты часто используемых возможностей и внести их в версионируемый registry. Для каждой — положительный пример, важный крайний случай, ограничения и исходники.
3. Классифицировать все 74 карты выбранных списков, включая уже реализованные. Добавить отдельную стратифицированную выборку до 100 collectible карт из сохранённого Standard-среза: простые эффекты, композиции, триггеры, случайная генерация, новые механики. Не выбирать только удобные примеры; сохранить IDs и правило отбора. Tokens/зависимости считать отдельным знаменателем.
4. На каждую карту записать маршрут AUTO / COMPOSABLE / MISSING_PRIMITIVE / CUSTOM / UNKNOWN, обоснование, нужные capabilities, зависимости, правила targeting, источники и нерешённые вопросы. AUTO означает пригодность для автоматизированного описания, а не уже доказанную корректность.
5. Выдать реальные количества с явными UNKNOWN и независимыми статусами верификации. Оставшиеся десять сложных карт не являются репрезентативной выборкой для всего Standard.
6. Сгруппировать отсутствующие возможности; ранжировать по числу реально разблокируемых карт, завершению колод, объёму зависимостей, ожидаемым трудозатратам и риску общей логики. Не суммировать пересекающиеся группы как независимые выигрыши.

Предлагаемые будущие артефакты: `reports/card_support_analysis_*.json`, `docs/CARD_SUPPORT_ANALYSIS.md`, `integrations/rosettastone/card_rules/capabilities.json`.

Готовность: есть проверяемый количественный отчёт, выбранная архитектура и список первого пакета. Пока этого нет, не начинать массовый ручной перенос следующих карт.

### Этап 2. Аудит зависимостей и честные статусы

1. Построить граф фиксированных зависимостей: tokens, enchantments, choose options, формы, созданные заклинания, оружие, силы героя и части существ.
2. Динамические пулы хранить как явные запросы: формат/патч, класс, тип, школа, раса, стоимость, источник и исключения. Если точный пул не выводится из данных, помечать UNKNOWN и указывать необходимость проверки.
3. Отдельно различать генерацию из собственной колоды и из всего формата. Первую часто можно ограниченно проверить; вторая может расширить зависимости до сотен карт. Циклы в графе разрешать через обход с visited/fixed point, не обрывать зависимости произвольной глубиной.
4. Для карты хранить независимые признаки metadata_present, rules_registered, route, verification_status, dependency_status, bridge_action_status. Статусы правил: UNSUPPORTED, PARTIAL, IMPLEMENTED_UNVERIFIED, VERIFIED_SCOPED. VERIFIED_SCOPED всегда сопровождается проверенной областью и известными ограничениями.
5. Дать колоде отдельный статус допуска: inventory_complete, scenario_checked, dependency_checked, match_smoke_passed, training_eligible. Старые два Warlock списка обозначить как исторические пилоты до проверки по новому gate; не объявлять их автоматически сертифицированными.
6. Для строгого режима неизвестная семантика или возможная неподдержанная зависимость блокирует допуск. Ошибка в runtime отклоняет весь эпизод и его метки. Не исключать неподдержанные карты из случайного пула молча: это меняет правила игры. Ограниченный исследовательский режим возможен только как явно обозначенная аппроксимация с отдельными результатами.

Готовность: отчёт отличает 64 регистрации от доказанной поддержки, показывает неизвестные зависимости и точную причину отказа каждой колоде. Этот этап развивается вместе с аудитом, а не после массового импорта.

### Этап 3. Узкий прототип деклараций и генератора

1. Выбрать пакет из 8–12 карт по результатам этапа 1: несколько реализованных аналогов для сравнения и несколько новых простых карт из полезного target pool. Начальные кандидаты для миграционного эксперимента: CORE_CS2_004, END_007, CAP_801, CORE_SW_066, CATA_302. Это кандидаты, а не заранее одобренные эталоны.
2. Формат v1 содержит schema_version, card_id, metadata/rules fingerprint, режим активации (spell play / Battlecry / Deathrattle), play requirements, упорядоченные операции, dependencies и provenance. Начальный allowlist: damage, heal, draw, armor, summon fixed ID, enchantment, destroy, freeze, silence, add fixed card. Подключать операции только когда они нужны пилоту.
3. Валидатор отклоняет неизвестные поля, операции, символы, типы целей, недопустимые параметры, неразрешённые ссылки и неподдержанные комбинации. Spell Damage, длительность и ownership нельзя угадывать общими defaults.
4. Генерация только через whitelist конкретных конструкторов/параметров; без eval, произвольных C++ вставок и свободных имён функций из JSON. LLM может подготовить черновик декларации, но schema validation не доказывает верность перевода текста.
5. Выводить отдельный generated cpp и manifest соответствия ID → декларация → зависимости → tests. Генерация детерминирована, воспроизводима и пишет файлы только при изменении содержимого; ошибки не оставляют частично обновлённый набор.
6. Подключить набор через CardDefs/CMake. Проверять дубли ID до запуска: `map.emplace` способен молча оставить старую реализацию. У каждого ID ровно один активный владелец — manual или generated. Старый блок убирать только после подтверждения эквивалентности; не делать массовую миграцию CoreCardsGen.cpp.
7. Экзотические случаи направлять в существующий native путь с явным статусом. Не раздувать язык ради одной легендарной карты.

Готовность: пакет работает через обычные Tasks; новые простые карты описываются параметрами; ошибки деклараций отвергаются до сборки/допуска.

### Этап 4. Сценарии, которые действительно проверяют правила

1. Переиспользовать небольшие fixture builders и параметризованные сценарии; проверять отдельно инфраструктуру генератора и семантику карты.
2. Генерировать механические smoke-проверки, но ожидаемые игровые результаты получать из независимо проверенных спецификаций. Тест, повторяющий ту же ошибочную IR, недостаточен.
3. Для миграционного пилота сравнить старый и generated путь на одинаковых детерминированных состояниях: здоровье, ресурсы, зоны, цели, события, выборы и завершение хода. Совпадение с прежним кодом не заменяет проверку правил, поскольку прежний код тоже может ошибаться.
4. По семействам проверить Spell Damage, отсутствие допустимой цели, обязательность цели, полный стол/руку, обработку смертей, Silence, срок зачарования и удвоение триггеров. Не строить декартово произведение всех случаев для каждой простой карты.
5. Случайные механики проверять на принадлежность результата legal pool и инварианты; для редких ветвей использовать контролируемые fixtures. Успешная случайная партия не покрывает весь пул.
6. Проверить bridge: видимые данные, легальные действия, окна выбора и отказ неподдержанных действий. Инфраструктурные данные о скрытых картах не передаются модели.

Готовность: есть независимая опора на правила и повторно используемые сценарии семейств, без необъяснённых регрессий.

### Этап 5. Ускорить сборку и измерить пользу

1. Создать один runner: validate → generate → configure при новых cpp → build core → build/relink bridge → family tests → короткий bridge smoke → coverage report.
2. Учесть реальные зависимости `.def`/headers и импортированный RosettaStone.lib. История сбоя Invalid game tag указывает на риск рассогласования; точный дефект отслеживания зависимостей ещё нужно воспроизвести, а не считать перенос тегов исчерпывающей диагностикой.
3. Новые внутренние теги добавлять в конец GameTagCustom.def, не сдвигая существующие значения. После изменений enum/ABI пересобирать всех потребителей. Контролировать identity сборки ядра и bridge, не ограничиваться успешным import.
4. Обычный пакет: одна инкрементальная сборка, один запуск выбранных сценариев и smoke моста. При сбое — повтор после исправления. Чистая сборка нужна при доказанной проблеме dependencies/ABI; не запускать её для каждой новой записи данных.
5. Generated cpp разбивать по семействам/пакетам, не создавать ещё один огромный файл, изменение которого компилирует всё содержимое.
6. На двух последовательных пакетах сравнить ручное время на карту, число ручных C++ блоков, число циклов исправлений, build time и долю отклонённых ошибочных деклараций. Ориентир успеха — примерно двукратное сокращение ручной работы для простых/составных карт при тех же проверках; это критерий эксперимента, не обещание.
7. Если выигрыша нет, упростить решение до templates/helpers. Не компенсировать плохой результат ростом универсальности DSL.

Готовность: известна фактическая экономия и принято решение о расширении. До этого этапа не обещать конкретные карты в час.
