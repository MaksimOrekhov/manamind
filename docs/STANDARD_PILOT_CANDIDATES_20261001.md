## Как провести первый пакет

1. Просмотреть восемь карт и ближайшие аналоги в CardSet source, определить их механические оси, owner, trigger timing и точные outcomes. Реестр пока не находит CardDef для этих восьми, поэтому приоритетно проверить runtime registration inventory и старые/legacy аналоги.
2. Для каждой карты зафиксировать предлагаемое представление: существующий Task composition, ограниченная декларация либо native handler. Не считать общий `DrawTask` достаточным объяснением карты.
3. Если общая модель не покрывает хотя бы 5–8 карт без небезопасных исключений, сузить пакет до подходящих карт или взять другую capability. Не добавлять condition language ради удержания размера пакета.
4. Подготовить независимые ожидаемые результаты для сценариев, включая empty deck, overdraw, условную границу и срабатывание триггера. Затем core build, bridge relink/smoke и fingerprints evidence.
5. Измерить ручные минуты, review/debug циклы, build time, исправления, число деклараций/native handlers и прирост `VERIFIED_SCOPED` roots/closure. До прохождения этих ворот pooled training остаётся заблокирован.

## Ограничения оценки

- Сигналы 104/159/189/77 построены по тексту, это не подсчёт механически одинаковых карт.
- Для восьми скрининговых карт мета-частота неизвестна. Пакет выбран по повторному использованию уже описанного `DrawTask` и проверяемости, а не по популярности.
- Кандидаты не получают `COMPOSABLE` автоматически. Их route остаётся UNKNOWN, пока не будет просмотрен source/effect contract.
- До регистрации карты необходимо подтвердить, что текущая движковая сборка соответствует проверяемым исходникам; scanner сам по себе этого не доказывает.

## Обновление pool detector

Реестр использует detector v2: 300 candidate signals от 282 Standard roots и 2 известных dependency origins (91 discover, 143 random-card/pool, 66 generated/history). v2 исключает случайные цели на игровом поле, фиксированные именованные summons и общие формулировки give/buff. Добавлены проверки на переносы строк, plural card types, Discover/random pools и history-dependent outcomes. Это сокращает шум эвристики; оно не доказывает, что все исключённые формулировки были ложными зависимостями или что оставшиеся сигналы точны. Точные selectors, members и engine parity требуют отдельной проверки.

## Source review: DrawTask

`DrawTask(amount, toStack)` многократно вызывает `Generic::Draw` и сообщает `COMPLETE`. `Generic::Draw` берёт верхнюю карту, при пустой колоде наносит очередной fatigue damage; обычное добавление в руку обрабатывает draw triggers, after-draw triggers и topdeck tasks. Полная рука обычно сжигает карту, кроме отдельной механики Godfrey set-aside. Флаг `toStack` дополнительно ставит реально взятые карты в task stack. Это проверенный общий примитив для взятия карты, но не контракт для выбора карты по фильтру или условий выполнения эффекта.

Кандидаты из исходного восьмёрочного списка каждый добавляют отдельную семантику: историю атак, временную блокировку сыгрывания, историю сыгранных существ, условие по стоимости взятой карты, размер колоды, проверку типов двух взятых карт либо счётчик Imbue. Поэтому этот список сам по себе не образует общий `DrawTask` package; генератор условия добавлять ради размера списка нельзя. `CAP_003` уже закрыта отдельным узким pilot. В source review обнаружен более предметный повторяемый участок: фильтрованный draw через уже существующие `DrawMinionTask`, `DrawSpellTask` и `DrawRaceMinionTask`. До добавления карточных регистраций нужно покрыть их контракт тестами: focused UnitTests для этих задач сейчас не найдены, а source inspection выявил обход requested count при недостатке подходящих карт. Решение и evidence зафиксированы в `docs/STANDARD_DRAW_TASK_SOURCE_AUDIT_20261001.md`.

## Результат первичного source/IR-аудита

Проверены восемь выбранных ID в `vendor/RosettaStone/Sources/Rosetta/PlayMode/CardSets` и в двух активных generated manifests. Для этих ID source CardDef не найден; они также не входят в bounded effect-composition allowlist. Это подтверждает `NO_DETECTED_RULE_REGISTRATION` текущего source inventory, но не заменяет прямую runtime-инвентаризацию собранной библиотеки.

**Решение:** набор годится как аудит DrawTask и независимых card contracts, но пока **не годится как первый code-generation ROI package**. Общим у карт является конечная операция draw; пакет должен был бы дополнительно внедрять/проверять минимум attack trigger, attack-history cost, hand lock duration, played-card history, conditional follow-up draw, deck-size condition, post-draw card-type condition и Imbue counter. Effect-composition schema поддерживает `DRAW` как последовательную операцию, но не эти триггеры/предикаты/длительности. Переименовать этот набор в простой DrawTask migration означало бы завысить повторное использование.

Проверенные опоры:

- `integrations/rosettastone/card_rules/capabilities.json` содержит source-contract review для `DrawTask`: normal draw action повторяется заданное число раз; fatigue, overdraw и draw triggers наследуются от обычного действия.
- `vendor/RosettaStone/Tests/UnitTests/PlayMode/Tasks/SimpleTasks/DrawTaskTests.cpp` содержит normal draw, exhaust, overdraw и комбинированные случаи. Эти тесты подтверждают общий примитив, а не эффекты восьми карт.
- `integrations/rosettastone/card_rules/effect_composition.v1.json` allowlist не включает ни одну из восьми карт; текущий IR не задаёт condition/trigger/temporary hand lock для них.

Следующее действие для пилотного выбора: фильтровать registry-кандидатов по всем required capabilities и независимым проверочным сценариям, затем вручную сверить 8–12 карт до кодирования. Если требуемые условия не разделяются одной reviewed capability, сузить пакет или выбрать другую ось. `DrawTask` остаётся подтверждённым общим примитивом, но данный список нельзя использовать для вывода об эффективности генератора.

Этот экран не стал пятым пакетом: сначала нужна общая проверенная семантика для условий или ещё более узкая механика с несколькими действительно одинаковыми корнями.

**Следующий отдельный измерительный пакет после исходного экрана:** фильтрованный Deathrattle draw закрыл только однородную пару `FIR_929` (Fire spell) и `RLK_511` (Frost spell). Генератор переиспользует `DrawSpellTask(SpellSchool, 1)`; 3 native scenarios / 27 assertions прошли. FIR_929 прошла bridge session/action smoke; RLK_511 прошла deck legality и native scenario, но session smoke ограничен отсутствующим Death Knight setup. Registry фиксирует две текущие `VERIFIED_SCOPED` записи, однако обе остаются вне обучения из-за незакрытой closure и полного профиля. `TLC_223` исключена из-за Kindred, `EDR_226` и `EDR_572` — из-за другой race-фильтрации и дополнительных эффектов. Подробный контракт и scope: [STANDARD_DRAW_TASK_SOURCE_AUDIT_20261001.md](STANDARD_DRAW_TASK_SOURCE_AUDIT_20261001.md).

**Результат измерительной серии на текущий момент:** три первоначальных capability-пакета, одна ограниченная проверка reuse alias-маршрута и узкое расширение filtered-school draw. Это пока не подтверждает целевую экономию ручного труда: исторический authoring baseline отсутствует, selection bias сохраняется, Death Knight session setup не покрыт, а полный Standard profile остаётся заблокирован. Для следующего пакета измерять время с первого изменения и сравнивать с явно выбранным ручным baseline.

## Пачка из четырёх keyword-only карт и одного оружия

`CORE_GIL_558` Swamp Leech (Lifesteal), `CORE_ULD_723` Murmy (Reborn), `EDR_486` Scorching Observer (Rush + Lifesteal), `END_031` Shade of the End Time (Stealth + Spell Damage +1), `RLK_067` Corrupted Ashbringer (Lifesteal weapon) имеют в pinned metadata только эти ключевые слова, без отдельного текста действия. Новый allowlist generator сверяет hash каталога, точный набор mechanics, тип карты и то, что текст исчерпывается разрешёнными keyword labels; неизвестные поля, mechanics, карточный тип, лишний текст и ownership collision останавливают генерацию. Он создаёт обычные пустые CardDefs, чтобы движок мог загрузить карты и применить intrinsic tags из metadata.

Native focused test прошёл (1 case / 6 assertions), bridge smoke прошёл для четырёх миньонов (Standard deck validation, session, opening hand, legal actions); `RLK_067` прошла Standard DK deck validation, но match session заблокирована известной проблемой DK setup. Registry suite — 9/9. Все пять регистраций остаются `IMPLEMENTED_UNVERIFIED`: smoke подтверждает путь загрузки/действий, но для тренировки отдельно нужны независимые сценарии механик и полная зависимость/профиль. `CORE_DRG_079` и другие карты с Elusive намеренно исключены: текущий движок не имеет нужного Elusive targeting contract. Реестр после этого пакета: 167 direct + 62 generated, 953 текстовых корня без найденной регистрации; closures и training-eligible по-прежнему 0. ## Пачка из пятнадцати derived Core aliases

После DBF-linked aliases найден дополнительный воспроизводимый случай: Standard `CORE_...` card без `countAsCopyOfDbfId`, где остаток ID после `CORE_` равен legacy ID, legacy metadata и registered CardDef существуют, а нормализованный rules text совпадает точно.
